# WARP Amnezia Manager

Bash-утилита для создания и управления конфигурациями Cloudflare WARP для клиентов семейства Amnezia.

Проект умеет:

- генерировать один или несколько WARP-конфигов;
- формировать `.conf` для AmneziaVPN / AmneziaWG;
- формировать `vpn://...` для импорта в AmneziaVPN;
- сохранять Cloudflare registration ID, management token и клиентский `public_key` в локальный реестр;
- добавлять к регистрации понятную метку и срок действия;
- просматривать и редактировать созданные регистрации;
- отзывать регистрацию по номеру из реестра;
- определять регистрацию по содержимому любого сохранённого `.conf`, даже если файл был переименован или первоначальная локальная копия давно удалена;
- использовать отдельную временную очередь `revoke/` для одиночного и массового отзыва конфигов;
- безопасно обрабатывать дубликаты, неизвестные/повреждённые конфиги и конфликты реестра;
- автоматически отзывать регистрации с истёкшим сроком;
- работать через интерактивное терминальное меню или обычные CLI-опции.

При поиске регистрации по файлу **имя и путь конфига не являются идентификатором**. Менеджер читает `PrivateKey` только из секции `[Interface]`, вычисляет соответствующий публичный ключ через `wg pubkey` и ищет точное совпадение с `registrations[].public_key`. Сам `PrivateKey` в реестре не сохраняется.

> **Рекомендация:** для каждого устройства лучше создавать отдельную WARP-регистрацию и отдельный конфиг. Так их проще подписывать, ограничивать по сроку и отзывать независимо друг от друга.

## Быстрый старт: Linux / WSL

Клонируйте репозиторий и перейдите в него:

```bash
git clone https://github.com/sar2718/warp-amnezia-manager.git
cd warp-amnezia-manager
```

Запустите:

```bash
bash warp_manager.sh
```

В интерактивном терминале откроется меню:

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  WARP Amnezia Manager
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Состояние локального реестра:
  ────────────────────────────────────────────────────────
  Активных:       3
  Скоро истекают: 1
  Просрочено:     0
  Отозвано:       2
  Без конфига:    0
  ────────────────────────────────────────────────────────

  [1] Создать конфигурации
  [2] Управление регистрациями
  [3] Проверить и отключить истёкшие
  [4] Справка
  [0] Выход
```

Навигация по интерфейсу выполняется цифрами. В меню `0` всегда означает возврат, отмену или выход. Буквенные команды для навигации не используются. Пустой `Enter` в меню ничего не выбирает — номер пункта нужно вводить явно.

Цветовая подсветка следует смыслу действия: обычные переходы и пункты, которые только открывают следующий экран, отображаются как обычные пункты меню. Красным выделяется только **финальное опасное действие**, после выбора которого действительно выполняется отзыв через API или удаление локального `.conf`. Поэтому, например, пункт `Отозвать все подходящие конфиги из revoke/` в меню остаётся обычным: сначала он лишь сканирует очередь и показывает план; красным будет уже отдельное подтверждение массового отзыва.

На Linux не требуется заранее определять дистрибутив. Если необходимых программ нет, скрипт определит доступный пакетный менеджер.

Поддерживаются:

- `apt-get` — Debian, Ubuntu, WSL на их основе;
- `pacman` — Arch Linux и производные;
- `dnf` — Fedora и производные;
- `zypper` — openSUSE;
- `apk` — Alpine Linux.

Основные зависимости: `curl`, `jq`, `wireguard-tools`, `util-linux` (`flock`) и `coreutils`.

Если зависимости уже установлены, пакетный менеджер не вызывается.

## Создание конфигурации через меню

Создание теперь работает как отдельный экран настроек, а не как длинная последовательность вопросов:

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  WARP Amnezia Manager › Создание
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Параметры новой партии:
  ────────────────────────────────────────────────────────
  Количество: 5
  Метки:      Выборочно — заполнено 3/5
  Срок:       30d
  ────────────────────────────────────────────────────────

  [1] Изменить количество конфигов
  [2] Настроить метки / комментарии
  [3] Настроить срок действия
  [4] Предпросмотр партии
  [5] Создать конфигурации
  [0] Отмена и возврат в главное меню
```

До фактической регистрации можно сколько угодно менять параметры и открывать предпросмотр.

### Метки и комментарии при пакетной генерации

Для одного конфига интерфейс предлагает просто оставить метку пустой или задать комментарий.

Если создаётся несколько конфигов, доступны пять вариантов:

1. оставить все регистрации без меток;
2. присвоить одну одинаковую метку всем конфигам;
3. использовать общую основу с автоматической нумерацией (`USER #1`, `USER #2`, ...);
4. задать метку каждому конфигу отдельно;
5. пометить только выбранные конфиги.

В выборочном режиме можно вводить номера и диапазоны:

```text
1,3,5-7
```

Например, при создании пяти конфигов можно указать метку только для `1,3,5`, затем отдельно другую метку для `2`, а `4` оставить без комментария. Перед созданием список можно просмотреть.

После создания метка каждой регистрации всё равно остаётся редактируемой отдельно через меню управления регистрациями. Поэтому ошибочная или временная подпись не требует пересоздания WARP-конфига.

### Срок действия

Для партии можно выбрать:

- бессрочно;
- 1 день;
- 7 дней;
- 30 дней;
- свой срок (`30m`, `12h`, `7d`, `4w`);
- конкретную дату окончания.

После создания срок отдельной регистрации можно изменить, продлить или сделать бессрочным через меню управления.

Дата, введённая без часового пояса (например `2026-12-31 23:59`), трактуется в локальном часовом поясе системы, где запущен скрипт. В реестре время сохраняется в UTC.

Срок хранится локально. Само значение `expires_at` не отключает WARP на стороне Cloudflare — для этого должен быть выполнен отзыв регистрации. Основная логика проверки и отзыва находится в `warp_manager.sh --revoke-expired`, а `warp_expiry.sh` — короткая обёртка для ручного запуска и будущего `systemd timer`.

## Где хранятся данные

После первого запуска структура выглядит примерно так:

```text
warp-amnezia-manager/
├── .data/
│   └── registrations.json
├── configs/
│   ├── WARP.conf
│   ├── WARP_1.conf
│   └── ...
├── revoke/
│   └── ...
├── tests/
│   └── test_revoke_workflow.sh
├── .gitignore
├── .replit
├── LICENSE
├── README.md
├── replit.nix
├── warp_expiry.sh
└── warp_manager.sh
```

`configs/`, `revoke/` и `.data/` автоматически создаются с закрытыми правами доступа. Все три директории исключены из Git.

### `configs/`

Временный выход генератора. Здесь появляются готовые `.conf` с `PrivateKey`.

После того как конфиг передан пользователю и больше не нужен на устройстве, локальный файл можно удалить. Удаление `.conf` **не удаляет** запись из `.data/registrations.json` и не мешает позже отозвать регистрацию по заново скачанному экземпляру того же конфига.

### `revoke/`

Временная очередь конфигов, которые нужно проверить или отозвать.

Типичный сценарий:

```text
Telegram / другое хранилище
        ↓ скачать старый .conf
revoke/
        ↓ PrivateKey -> wg pubkey
registrations.json
        ↓ id + token
Cloudflare API DELETE
```

Можно положить в `revoke/` один или несколько `.conf`. Менеджер умеет выбрать один файл либо сначала просканировать всю директорию, показать план и только затем выполнить массовый отзыв.

Файлы из `revoke/` **не удаляются автоматически**. После успешного интерактивного отзыва менеджер может отдельно предложить удалить только успешно обработанные файлы. При использовании `--yes` удаление файлов никогда не выполняется.

### `.data/registrations.json`

Единый локальный реестр всех регистраций, созданных этим экземпляром проекта.

Пример записи:

```json
{
  "id": "registration-id",
  "token": "management-token",
  "public_key": "wireguard-client-public-key",
  "config": "configs/WARP.conf",
  "label": "USER — iPhone",
  "created_at": "2026-09-09T15:30:00Z",
  "expires_at": "2026-10-09T15:30:00Z",
  "revoked_at": null,
  "revoke_reason": null
}
```

`public_key` — стабильная связь между выданным конфигом и регистрацией. Для новых регистраций менеджер не допускает повторное использование одного и того же client public key.

Поле `config` остаётся метаданными о первоначально созданном локальном файле. Оно **не используется** для поиска регистрации по `.conf` и может повторяться у разных записей, если старые файлы удалялись и имя `WARP.conf` использовалось снова.

`PrivateKey` в реестре не хранится.

> **Важно:** `.data/registrations.json` содержит management token регистраций WARP. Этот файл нельзя публиковать или передавать другим пользователям.

## Как работает поиск по старому конфигу

Допустим, конфиг был создан, отправлен человеку и удалён с компьютера. Через несколько месяцев файл можно снова скачать из старого чата и передать менеджеру:

```bash
bash warp_manager.sh --revoke ~/Downloads/WARP.conf
```

Менеджер выполняет следующую последовательность:

```text
[Interface] PrivateKey
        ↓
     wg pubkey
        ↓
client public_key
        ↓ точное совпадение
.data/registrations.json
        ↓
registration id + token
        ↓ после подтверждения
Cloudflare API DELETE
```

Имя файла может быть любым: `WARP.conf`, `old.conf`, `андрей.conf` и т.д. Переименование файла на сопоставление не влияет.

Для защиты от ошибочного отзыва:

- учитывается только `PrivateKey` из секции `[Interface]`; `[Peer] PublicKey` для идентификации не используется;
- отсутствие `PrivateKey`, несколько `PrivateKey` в `[Interface]` или ключ, который не принимает `wg pubkey`, считаются ошибкой;
- если вычисленный public key отсутствует в реестре, ничего не отзывается;
- если одному public key неожиданно соответствуют несколько записей реестра, это считается конфликтом целостности и отзыв блокируется;
- поддерживаются обычные Unix-переносы строк и CRLF;
- произвольный файл за пределами `revoke/` менеджер никогда не удаляет.

## Управление регистрациями

Откройте:

```bash
bash warp_manager.sh
```

и выберите:

```text
[2] Управление регистрациями
```

В меню регистраций можно:

- открыть конкретную запись по номеру;
- изменить одну метку;
- массово назначить одну метку выбранным номерам или сразу всем регистрациям;
- изменить дату окончания;
- продлить срок;
- сделать регистрацию бессрочной;
- открыть отдельное меню отзыва;
- проверить истёкшие записи;
- посмотреть техническую информацию.

Для массового изменения меток поддерживаются номера и диапазоны, например `1,3,5-7`. Пустая новая метка очищает комментарий у выбранных записей.

Токен управления в интерфейсе не выводится открытым текстом.

### Меню отзыва

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  WARP Amnezia Manager › Регистрации › Отзыв
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Файлов в revoke/:       4
  ────────────────────────────────────────────────────────

  [1] Отозвать по номеру регистрации
  [2] Отозвать один конфиг из revoke/
  [3] Отозвать конфиг по указанному пути
  [4] Отозвать все подходящие конфиги из revoke/
  [0] Назад
```

### Отзыв по номеру

```bash
bash warp_manager.sh --list
bash warp_manager.sh --revoke 2
```

### Отзыв по любому файлу в системе

```bash
bash warp_manager.sh --revoke ~/Downloads/WARP.conf
```

Можно передать абсолютный или относительный путь. В интерактивном поле также поддерживается `~/...` и путь, вставленный в одинарных или двойных кавычках.

Поиск по имени или по старому значению `config` в JSON отсутствует намеренно: файл должен физически существовать, чтобы менеджер мог определить его по `PrivateKey`.

### Один файл из `revoke/`

Положите `.conf` в `revoke/`, затем в интерактивном меню выберите пункт `Отозвать один конфиг из revoke/`.

Перед отзывом показывается найденная запись: метка, маскированный client public key, дата создания, срок и статус. После успешного отзыва можно отдельно удалить файл из очереди или оставить его.

### Все конфиги из `revoke/`

Через меню можно сначала просканировать всю очередь. CLI-вариант:

```bash
bash warp_manager.sh --revoke-dir
```

До API-запросов менеджер выводит классификацию файлов:

```text
ГОТОВ К ОТЗЫВУ
УЖЕ ОТОЗВАН
НЕ НАЙДЕН В РЕЕСТРЕ
НЕКОРРЕКТНЫЙ КОНФИГ
ДУБЛИКАТ
КОНФЛИКТ РЕЕСТРА
```

Одинаковые конфиги под разными именами не приводят к повторному DELETE: в одной пачке одинаковый public key обрабатывается один раз.

Сам пункт массовой обработки в меню не считается опасным действием и не выделяется красным: его выбор только запускает анализ файлов. После показа плана менеджер отдельно выводит красный пункт подтверждения с точным числом регистраций, которые будут отозваны.

Если один API-запрос завершился ошибкой, обработка остальных подготовленных регистраций продолжается. В конце выводится сводка успешных отзывов, ошибок и пропущенных файлов. Локальная запись помечается `revoked_at` только после успешного ответа API.

Для неинтерактивного запуска:

```bash
bash warp_manager.sh --revoke-dir --yes
```

`--yes` подтверждает отзыв, но **никогда не подтверждает удаление `.conf`**.

### Массовая обработка произвольной директории

Можно указать другую директорию:

```bash
bash warp_manager.sh --revoke-dir ~/Downloads/old-warp
```

Сканируется только верхний уровень и только `*.conf`. Файлы в произвольной директории после обработки не удаляются менеджером.

### Отзыв по Cloudflare registration ID

```bash
bash warp_manager.sh --revoke-id <registration-id>
```

Registration ID ищется в локальном реестре; для фактического DELETE используется сохранённый management token.

После успешного ручного отзыва в JSON записываются:

```json
"revoked_at": "2026-09-09T16:00:00Z",
"revoke_reason": "manual"
```

Для массового отзыва через директорию причина записывается как `manual-batch`.

## Автоматический контроль сроков

Основная логика проверки сроков находится в `warp_manager.sh` и доступна через:

```bash
bash warp_manager.sh --revoke-expired
```

Для удобства в репозитории есть короткая обёртка:

```bash
bash warp_expiry.sh
```

При запуске выполняется одна и та же логика:

1. читается `.data/registrations.json`;
2. находятся записи с истёкшим `expires_at`;
3. уже отозванные регистрации пропускаются;
4. выполняется отзыв через Cloudflare API;
5. только после успешного ответа обновляется JSON.

При автоматическом отзыве:

```json
"revoke_reason": "expired"
```

Перед реальным отзывом можно выполнить безопасную проверку:

```bash
bash warp_expiry.sh --dry-run
```

Для будущего запуска через `systemd timer` предусмотрен тихий режим:

```bash
bash warp_expiry.sh --quiet
```

`warp_expiry.sh` не содержит отдельной копии бизнес-логики и просто вызывает `warp_manager.sh --revoke-expired`. Он не висит в памяти постоянно. Позже его можно запускать по расписанию через `systemd timer` на сервере.

## CLI

Интерактивный интерфейс является основным способом ручной работы, но вся базовая функциональность доступна и через CLI.

### Генерация

Один бессрочный конфиг:

```bash
bash warp_manager.sh --generate
```

Пять конфигов:

```bash
bash warp_manager.sh --generate --count 5
```

С меткой и сроком 30 дней:

```bash
bash warp_manager.sh \
  --generate \
  --label "USER — iPhone" \
  --ttl 30d
```

До конкретной даты:

```bash
bash warp_manager.sh \
  --generate \
  --label "USER" \
  --expires "2026-12-31 23:59"
```

Старые короткие варианты также работают:

```bash
bash warp_manager.sh -n 5
bash warp_manager.sh -n 3 -q
```

### Список

```bash
bash warp_manager.sh --list
```

### Отзыв

По номеру:

```bash
bash warp_manager.sh --revoke 2
```

По содержимому конкретного файла:

```bash
bash warp_manager.sh --revoke ~/Downloads/WARP.conf
```

Вся стандартная очередь `revoke/`:

```bash
bash warp_manager.sh --revoke-dir
```

Произвольная директория:

## Что происходит при ошибке

Registration ID и token сохраняются в реестр сразу после успешного `POST /reg`.

Поэтому если позже не сработал `PATCH`, не удалось получить параметры туннеля или записать `.conf`, созданная Cloudflare-регистрация не теряется: она остаётся доступна для последующего отзыва по номеру/ID.

Обновление `registrations.json` выполняется через временный файл и атомарную замену. Параллельная запись защищается `flock`.

Для client public key действуют две проверки уникальности:

1. перед `POST /reg` менеджер проверяет, что ключ ещё не присутствует в реестре;
2. перед фактической записью новой регистрации проверка повторяется уже под блокировкой `flock`.

Если между этими этапами возник редкий конфликт из-за параллельного запуска, менеджер не создаёт неоднозначную локальную запись и пытается немедленно отозвать лишнюю удалённую регистрацию.

Если в этом редком сценарии не удаётся ни записать регистрацию в основной реестр, ни выполнить автоматический откат через API, менеджер сохраняет `id`, management token и client public key в отдельный `.data/recovery-*.json` с правами `600`. Это аварийная страховка от потери управления регистрацией; после успешного ручного отзыва или восстановления записи такой recovery-файл можно удалить. Только если файловая система не позволяет создать даже recovery-файл, `id/token` выводятся в терминал как последнее средство восстановления.

Если пользователь передал одновременно `PRIVATE_KEY` и `PUBLIC_KEY`, перед обращением к Cloudflare проверяется, что public key действительно вычисляется из этого private key.

При отзыве локальная запись получает `revoked_at` только после успешного ответа Cloudflare API. Если API недоступен или вернул ошибку, запись остаётся активной и операцию можно повторить позже.

При массовом отзыве ошибка одного файла/API-запроса не прерывает обработку остальных подготовленных регистраций.

## Прерывание `Ctrl+C`

Уже успешно созданные `.conf` остаются на диске.

Регистрации, для которых Cloudflare уже успел вернуть `id/token`, также сохраняются в локальном реестре.

## Импорт в приложения

Генерируемый `.conf` содержит дополнительные параметры AmneziaWG (`S1`, `S2`, `Jc`, `Jmin`, `Jmax`, `H1..H4`, `I1`). Поэтому он предназначен для клиентов, которые поддерживают соответствующий формат AmneziaWG.

Совместимость конкретного `.conf` может зависеть от приложения и его версии. Для AmneziaVPN дополнительно формируется ссылка `vpn://...`, предназначенная для импорта именно в AmneziaVPN.

Обычный WireGuard не поддерживает дополнительные параметры AmneziaWG.

- `.conf` — конфигурация с параметрами AmneziaWG;
- `vpn://...` — ссылка импорта для AmneziaVPN.

При пакетной генерации секретное содержимое каждого конфига не выводится огромной простынёй в терминал — показываются созданные файлы.

## Удалённые среды

Генератор можно запускать в обычной Linux-среде, WSL, GitHub Codespaces, Replit и на VPS.

Файлы `.replit` и `replit.nix` намеренно остаются в репозитории: `.replit` запускает `bash warp_manager.sh`, а `replit.nix` подключает Bash, WireGuard Tools, `jq`, `curl`, `coreutils` и `util-linux`, необходимые менеджеру в Replit.

Доступность consumer WARP API зависит от сети. Если API не отвечает из вашей текущей сети, можно использовать другую сеть или удалённую Linux-среду.

Для полноценного управления регистрациями лучше использовать постоянную копию репозитория.

Если создать конфиги во временной среде и затем удалить всю среду вместе с `.data/registrations.json`, будут потеряны токены, необходимые этому менеджеру для последующего отзыва созданных регистраций.

Поэтому для конфигов со сроком действия сохраняйте `.data/registrations.json` в безопасном месте или запускайте проект на постоянном сервере.

## Безопасность и Git

В проектном `.gitignore` исключены:

```gitignore
.data/
configs/
revoke/
```

В Git не должны попадать:

- реальные `.conf` из `configs/` или `revoke/`;
- `PrivateKey`;
- `.data/registrations.json`;
- WARP management token.

`PrivateKey` из файла на отзыв читается только в память процесса и передаётся через stdin в `wg pubkey`. Менеджер не записывает его в JSON и не использует как аргумент командной строки.

Файлы из произвольных директорий менеджер не удаляет. Файлы из `revoke/` могут быть удалены только после успешного отзыва, отдельного интерактивного подтверждения и повторной проверки, что содержимое файла не изменилось после сопоставления.

Перед публикацией изменений полезно проверить:

```bash
git status
git ls-files
```

## Локальные тесты

В `tests/test_revoke_workflow.sh` находится тестовый сценарий новой логики отзыва. Он работает во временной директории, подменяет `wg` и `curl` локальными mock-командами и **не выполняет реальные запросы Cloudflare**.

Запуск:

```bash
bash tests/test_revoke_workflow.sh
```

Проверяются, в частности:

- поиск по содержимому файла, а не по имени;
- путь с пробелами и CRLF;
- игнорирование `[Peer] PublicKey`;
- неизвестный/повреждённый конфиг;
- несколько `PrivateKey`;
- конфликт одинакового `public_key` в реестре;
- дубликаты в `revoke/`;
- продолжение массовой обработки после ошибки API;
- отсутствие автоматического удаления при `--yes`;
- запрет повторного client public key до обращения к API;
- проверка согласованности переданных `PRIVATE_KEY`/`PUBLIC_KEY`;
- отсутствие `PrivateKey` в `registrations.json`.
